# Security

Please report vulnerabilities privately through GitHub's [private vulnerability reporting](https://github.com/harish-anumula/inpage/security/advisories/new), not in a public issue. Expect a reply within a week.

## Threat model and defences

- **Web pages are untrusted.** Page text reaches the model wrapped in random markers and labelled as data; every system prompt tells the model never to follow instructions inside it (`extension/prompts.js`, `IP.untrusted` in `src/core.js`). `test/injection.mjs` checks a page that tries to hijack the model. With Jev on, each page is also checked once for text aimed at AI assistants, and the drawer warns the reader when it finds some (it caught 9 of 9 instructions hidden in a long page in testing); this is a warning, not the defence: the markers and the sanitiser apply either way.
- **Model output is untrusted.** Everything the model writes goes through DOMPurify with a short allowlist of text and table elements before it touches the page or a frame (`src/render.js`): no scripts, styles, forms, iframes, SVG, MathML, media or event handlers; links only `http(s)`, `mailto` or `#`; and no attribute that names a resource (`src` only for images that were already in the block, no `poster`, `srcset`, `background`, `ping` and the like). Citation chips are added by walking the cleaned tree's text, never by editing its HTML. So a model can't make the browser fetch an attacker's address with the conversation in it; as a second wall, the extension's own pages allow no images from the web at all (`img-src 'self' data: blob:`), and image previews there come through the service worker under the image rules below. `test/sanitize.mjs` runs 20 such payloads through the shipped code.
- **The page can't trigger edits.** A planner reads the page outline to pick which blocks to change, but page-wide edits run only when the reader's own request starts with an edit ("add…", "rewrite…", "simplify…"); neither the planner nor Jev, which both see text the page controls, can authorise one.
- **Your questions and answers stay out of the page.** Conversations live in the browser's side panel, outside the page altogether (or, if you choose, in a frame inside it). The composer and the in-page drawer are extension pages (`extension/ui/frame.html`) in iframes. The page can't read them, can't click or type into them, and doesn't receive the keys you type there. They talk to the content script over a `chrome.tabs.connect` port, which pages can't open or listen to, and the content script accepts it only from this extension's frame page. The frame is served from a per-session address (`use_dynamic_url`). Only the browser's own side panel (a top-level page that isn't in a tab) may act as the panel, so a copy of the frame page loaded inside a web page or opened as a tab can't take a conversation over. The selection toolbar, status chips, edit controls and pins sit in a closed shadow root. `test/isolation.mjs` checks all of this from a page's own scripts.
- **Other tabs and the screen.** Only the extension's own pages and worker can ask a tab for its text, and only for tabs in the same window, when you ask; quotes are checked in their own tab by the content script there. A video frame is captured only while the asking tab is the one on screen; a capture during which any tab was switched (even away and back) is thrown away. Frames are kept out of saved notes.
- **Your typing on the page.** Form fields, comment and message boxes are left out of every piece of page text sent (the page text, outlines, passages, nearby text and fact-check), through one shared filter (`IP.textOf`).
- **The API key.** Stored in `chrome.storage.local` with access level `TRUSTED_CONTEXTS`, so content scripts and pages can't read it; only the service worker uses it, and it is sent only to `openrouter.ai`.
- **Messages and storage.** The service worker accepts messages only from this extension (`sender.id`), checks their shape and refuses to hand out the key. A content script can read and write only its own site's records; every record is rebuilt to a fixed shape (ids, statuses, verdicts, numbers, size) when it's saved, loaded or restored from a backup, and the views escape every value they show.
- **Scripted clicks.** Every inpage control on the page checks that a click or key came from the reader (`isTrusted`), even if the control is taken out of its shadow root, so nothing can run a paid action without the reader.
- **Image fetches.** Only public `http(s)` images (no localhost, private, link-local or IPv6-literal addresses, in any spelling, trailing dots included; no user names in the address; no other schemes), fetched without cookies and without following redirects, `image/*` only, stopped at 4 MB. An image that fails these rules isn't sent at all.
- **Supply chain.** Libraries are vendored at exact versions with checksums (`extension/lib/VERSIONS.*`); their licenses are in `extension/lib/LICENSES/`. Nothing is loaded from a CDN, and no code from outside the package runs: the model's output is only ever text and sanitised HTML. CI actions are pinned to commit SHAs.

## Known limits

- Rewrites and inserted answers go into the page itself, so the page can read them, like any other text on it.
- KaTeX's styles and fonts are served at the extension's fixed address (they can't use a per-session one: the browser resolves the fonts' relative links back to the fixed address and blocks them), so a page could detect that inpage is installed by probing for them.
- While the composer is open (and with the in-page drawer), the page holds an extension frame; Chrome then blocks other extensions that use the debugger (such as Claude in Chrome) from that tab. inpage removes its frames as soon as they close.
- The page can see that an iframe exists and could cover it or move it (clickjacking); it can't read it or act inside it.
- Another extension with access to the page can read what inpage shows in the page itself (the toolbar, a recalled glossary card, rewrites), as it can read the rest of the page; it can't read the composer, the side panel or the key.
- A host name that resolves to a private address isn't caught (an extension can't see DNS answers); such fetches carry no cookies, and only an image response is used.
- A video frame is a picture of the screen area where the video is, including anything drawn over it.
- inpage's content scripts on any site can read your glossary and reading bookmarks (that's how a term you asked about elsewhere is recalled); pages themselves can't.
- With Jev on, a question can switch on web search for itself (about $0.005) when Jev judges it needs current information; glossary definitions are written by the model and kept in this browser.
- Content scripts run on all sites so the selection toolbar is always there; an opt-in, `activeTab`-only mode is on the roadmap.
